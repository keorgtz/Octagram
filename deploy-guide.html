Guía de Deploy Limpio · OctagramDelivery

Solución completa para ver cambios nuevos tras un deploy con Docker + Blazor PWA

!
¿Por qué no ves los cambios?
Hay 3 causas típicas, ordenadas de más a menos probable
Causa #1 — Más común (90%) Blazor WebAssembly es una PWA con Service Worker. El service worker guarda en caché todos los .wasm, .js y CSS en el navegador. Aunque el servidor tenga el código nuevo, el navegador sigue ejecutando la versión vieja hasta que el service worker se actualice. Esto pasa incluso con F5 normal.
Causa #2 — Docker build cache docker compose up -d --build reutiliza capas de Docker si detecta que los archivos copiados no cambiaron (por timestamps o por hash). A veces la capa de dotnet publish se reutiliza incluso con código nuevo.
Causa #3 — Caché del navegador normal El navegador puede servir CSS/JS viejos desde su caché local sin consultar al servidor.
1
Verificar que el código está en el servidor
Ejecutar en el servidor (SSH)
SSH al servidor
# Ver qué commit tiene el servidor git log --oneline -3 # Debe mostrar el commit más reciente: # 2f68d41 Fix Cards & Add Groups ← este es el último # Si no coincide, hacer pull: git pull origin Master
✓ El commit 2f68d41 "Fix Cards & Add Groups" contiene todos los cambios de vistas móviles, buscadores, grupos de clientes y migración de base de datos.
2
Rebuild de Docker sin caché
Ejecutar en el servidor. Esto garantiza que se compila el código nuevo.
⚠ Antes de ejecutar: docker compose down detiene los contenedores. La app quedará inaccesible por 1–3 minutos mientras reconstruye.
Rebuild completo sin caché de Docker
# 1. Bajar contenedores docker compose down # 2. Eliminar imágenes viejas del proyecto docker compose build --no-cache # 3. Levantar contenedores con la imagen nueva docker compose up -d # 4. Verificar que arrancaron correctamente docker compose ps docker compose logs --tail=30

Si quieres también limpiar volúmenes y redes huérfanas (más agresivo):

Limpieza profunda (opcional)
# Eliminar contenedores + volúmenes anónimos docker compose down -v # Limpiar imágenes/capas sin usar docker system prune -f # Rebuild y levantar docker compose up -d --build
ℹ docker system prune -f no elimina volúmenes con nombre (tus datos de base de datos están seguros si usan un volumen nombrado).
3
Aplicar migración de base de datos
Solo si usas SQL Server local en el servidor (no en Docker separado)

⚠ Migración requerida: AddCustomerGrupo

Se agregó la columna Grupo a la tabla Customers. Si no aplicas esta migración, la API dará error 500 al consultar clientes.

Opción A — dotnet ef en el servidor
cd /ruta/al/proyecto dotnet ef database update \ --project OctagramDelivery.Infrastructure \ --startup-project OctagramDelivery.Api
Opción B — Si la API aplica migraciones al iniciar (Program.cs)
# Si tu app.cs tiene: context.Database.MigrateAsync() # entonces la migración se aplica automáticamente al iniciar el contenedor. # Verificar en los logs: docker compose logs api --tail=50 | grep -i migrat
4
Limpiar el Service Worker en el navegador
Este paso es el más importante — sin él, el navegador sigue usando la versión vieja aunque el servidor tenga la nueva
🔴 Este es el verdadero culpable. Blazor PWA registra un service worker que guarda en caché todos los archivos .wasm, .js y CSS con hashes únicos. Un F5 normal NO los limpia. Necesitas forzar la actualización.

Método rápido para ti (desarrollador):

Chrome / Edge
  • Abre la app
  • F12 → pestaña Application
  • Sidebar → Service Workers
  • Click Unregister
  • Sidebar → Storage → Clear site data
  • Recargar la página
Firefox
  • Abre la app
  • F12 → pestaña Application
  • Sidebar → Service Workers
  • Click Unregister
  • Recargar
Hard Refresh (atajo rápido)
  • Cierra TODAS las pestañas de la app
  • Reabre la app
  • Presiona Ctrl+Shift+R
  • Si no funciona, usa el método de DevTools
Celular (Chrome Android)
  • Ir a Configuración del sitio (ícono 🔒 en URL)
  • → Almacenamiento
  • → Borrar datos
  • Recargar la app
✓ Para tus usuarios finales: el service worker de Blazor detecta automáticamente que hay una nueva versión (por el hash de service-worker-assets.js). Ellos solo necesitan cerrar todas las pestañas y volver a abrir la app. En la próxima visita verán un mensaje "nueva versión disponible" o la actualización se aplica sola.
5
Verificar que el deploy fue exitoso
Comandos para confirmar que todo funciona
Verificación en el servidor
# Ver contenedores corriendo docker compose ps # Ver logs recientes del API (buscar errores) docker compose logs api --tail=50 # Ver logs del frontend/nginx docker compose logs client --tail=50 # Confirmar que el commit correcto está desplegado git log --oneline -1 # Debe decir: 2f68d41 Fix Cards & Add Groups

Lista de verificación final:

  1. git log muestra el commit correctoEl servidor tiene 2f68d41 Fix Cards & Add Groups
  2. docker compose ps muestra todos los servicios como "Up"No debe haber servicios en estado "Exit" o "Restarting"
  3. Migración aplicadaLa tabla Customers tiene la columna Grupo (nullable varchar)
  4. Service worker limpio en el navegadorDevTools → Application → Service Workers muestra la versión nueva
  5. La app carga sin errores en consolaF12 → Console no tiene errores en rojo de recursos 404 o 500

Evitar este problema en futuros deploys
Mejoras al proceso de deploy
Script de deploy recomendado (guardar como deploy.sh en el servidor)
#!/bin/bash # deploy.sh — ejecutar en el servidor con: bash deploy.sh echo "[1/4] Pulling latest code..." git pull origin Master echo "[2/4] Stopping containers..." docker compose down echo "[3/4] Building without cache..." docker compose build --no-cache echo "[4/4] Starting containers..." docker compose up -d echo "Done! Containers status:" docker compose ps
ℹ Para usuarios finales que usan la PWA instalada en celular: cuando publiques una versión nueva, notifica en tu grupo de WhatsApp que cierren la app completamente y la vuelvan a abrir. Blazor PWA se actualiza sola en la siguiente apertura.
